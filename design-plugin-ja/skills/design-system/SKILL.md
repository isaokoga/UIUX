# /design-system

> 見慣れないプレースホルダがある場合や、どのツールが連携されているか確認したい場合は、[CONNECTORS.md](../../CONNECTORS.md) を参照してください。

デザインシステムを管理します — 一貫性の監査、コンポーネントのドキュメント化、新しいパターンの設計。

## 使い方

```
/design-system audit                    # システム全体の監査
/design-system document [コンポーネント]   # コンポーネントをドキュメント化
/design-system extend [パターン]          # 新しいコンポーネントやパターンを設計
```

## デザインシステムの構成要素

### デザイントークン
視覚言語を定義する最小単位の値:
- 色（ブランド、セマンティック、ニュートラル）
- タイポグラフィ（スケール、ウェイト、行間）
- スペーシング（スケール、コンポーネントのパディング）
- 境界線（角丸、幅）
- シャドウ（エレベーションのレベル）
- モーション（長さ、イージング）

### コンポーネント
以下が定義された再利用可能なUI要素:
- バリアント（primary、secondary、ghost）
- 状態（default、hover、active、disabled、loading、error）
- サイズ（sm、md、lg）
- 挙動（インタラクション、アニメーション）
- アクセシビリティ（ARIA、キーボード）

### パターン
コンポーネントを組み合わせた一般的なUIの解決策:
- フォーム（入力グループ、バリデーション、送信）
- ナビゲーション（サイドバー、タブ、パンくず）
- データ表示（テーブル、カード、リスト）
- フィードバック（トースト、モーダル、インラインメッセージ）

## 原則

1. **創造性より一貫性** — システムは、チームが車輪の再発明をしないために存在する
2. **制約の中での柔軟性** — コンポーネントは硬直的ではなく、組み合わせ可能であるべき
3. **すべてをドキュメント化する** — ドキュメント化されていなければ、それは存在しないのと同じ
4. **バージョン管理と移行** — 破壊的変更には移行手順が必要

## コネクタが利用可能な場合

**~~design tool** が連携されている場合:
- Figma 上で直接コンポーネントを監査する — 命名、バリアント、トークン使用を確認する
- ドキュメント化のためにコンポーネントのプロパティやレイヤー構造を取得する

**~~knowledge base** が連携されている場合:
- 既存のコンポーネントドキュメントや利用ガイドラインを検索する
- 更新したドキュメントを wiki に公開する

## ヒント

1. **まず監査から始める** — どこへ向かうか決める前に、現在地を把握しましょう。
2. **作りながらドキュメント化する** — 設計中にドキュメント化するほうが簡単です。
3. **完璧さより網羅性を優先する** — 10個のコンポーネントを100%ドキュメント化するより、全体の80%をドキュメント化するほうが勝ります。
